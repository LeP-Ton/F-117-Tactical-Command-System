# F-117 Tactical Command System（F-117 战术指挥系统）

[简体中文](README.md) | [English](README.en.md)

一款以有限情报、航线解谜和跨任务动态规划为核心的军事模拟游戏。玩家不直接操纵飞机，而是以任务指挥人员的身份，为 F-117 规划渗透、打击与撤离航线，并在任务持续执行时调整尚未抵达的未来航段。

- 在线版本：<https://lep-ton.github.io/F-117-Tactical-Command-System/>
- 精确规则与数值：[游戏机制手册](docs/game-mechanics.md)
- 技术栈：React 18、TypeScript、Vite、HTML Canvas、Vitest
- 游戏界面：简体中文 / English，可在任何页面通过语言选择弹窗切换

本文是项目的设计与开发入口，重点解释系统为什么存在、彼此如何协作，以及扩展代码时必须维护哪些边界。所有会随平衡调整变化的数值、阈值、状态转换和奖励公式只在游戏机制手册中维护。

## 1. 产品定位与设计哲学

### 1.1 解谜对象不是静态最短路

地图同时存在雷达覆盖与扫描、地形遮蔽、动态天气、燃油上限、目标区防御和撤离要求。安全航线不是绕开几个圆，也不是寻找一条几何最短路，而是在风险、距离、时间和情报误差之间构造具有容错空间的路线。

航向本身也是决策的一部分。F-117 的侧向暴露、在覆盖区内停留的时间，以及进入天气后产生的速度变化，都会让两条长度相近的路线拥有完全不同的风险。任务开始后世界继续运行，玩家只能调整当前目标航点之后的未来航段，因此规划与实时修正共同构成解谜过程。

### 1.2 信息不对称是核心资源

玩家看到的是战前雷达报告和机载告警，敌方看到的是雷达产生的带误差观测。正常视图下双方都不直接拥有完整真值：

```text
玩家侧：真实战场 → 有限雷达情报 → 航线判断
敌方侧：飞机真值 → Radar Sensor → 不完美 Contact → Belief → Commander
```

情报行动改变玩家能观察到什么，而不强化飞机，也不削弱真实雷达。完整敌方态势是可解锁的观察权限；它将同一套敌方内部系统可视化，但不会改变探测、指挥、交战或任务结果。

### 1.3 随机性必须可复现、可解释

游戏包含概率探测，但不依赖不可追踪的全局随机。行动代码、任务节点、雷达身份和扫描序列共同决定随机流。相同版本、相同任务历史、相同操作和相同时间演进能够复现结果，玩家因此可以比较路线、复盘失败并验证策略。

行动代码只定义基础世界。任务选择、失败次数、敌方警戒和历史航迹会继续改变后续部署，所以“相同 Seed”不等于忽略玩家行为后永远得到同一张战场。

### 1.4 长期成长作用于战场

项目没有装备构筑、飞机属性成长或任务后随机奖励。前置任务分别改变信息、扫描时间、覆盖空间和雷达协同；敌方则通过跨任务警戒与航迹画像回应玩家。

玩家构筑的是最终任务的战场条件，而不是一架数值更高的 F-117。这让任务网络中的选择始终回到同一个核心问题：后续航线会因这次行动变得更可知，还是让真实防空体系变得更弱？

### 1.5 沉浸界面与规则说明分层

任务界面模拟战术终端，只呈现任务状态、情报、告警、航点和传感器读数。不会在飞行界面直接解释投弹半径、概率公式或生成算法。

顶部“操作说明”提供玩家完成决策所需的简明提示；精确规则集中在机制手册；本 README 则记录设计意图、系统关系和开发边界。

### 1.6 双语只改变表达层

顶部语言按钮打开可扩展的语言选择弹窗。任务网络、三类战术工作区、Canvas 地图、操作说明、事件、天气和敌方内部面板都使用同一套语言目录。

语言偏好独立保存，不进入任务状态、Seed 或复盘快照。切换语言不会派发游戏动作、暂停模拟、重建任务或改变探测结果。领域层保留稳定枚举与存档值，只在渲染边界进行本地化。

## 2. 系统总览

```text
行动代码
  ├─ 生成任务网络与每个节点的基础世界
  ├─ 生成地形、天气、雷达、目标与有限情报
  └─ 派生可复现的扫描、预报与增援随机流

任务网络选择
  ├─ 改变情报权限、雷达扫描、雷达覆盖或指挥链
  ├─ 累积敌方警戒
  └─ 向敌方适应系统提供已飞航迹

单次任务
  ├─ 航线规划与未来航段实时调整
  ├─ Radar → Contact → Belief → Commander → Engagement
  └─ 摧毁目标并撤离，或失败后返回网络重试
```

这些系统不是彼此独立的功能清单。天气同时影响隐蔽与速度，扫描速率同时影响动画和真实探测频率，指挥链同时影响命令响应与多雷达证据共享。设计要求每个界面参数都能追溯到真实模拟作用。

## 3. 单次任务循环

一次任务由规划、持续执行、打击、撤离和结算组成：

1. 从任务网络进入可执行节点，在战术地图规划航点。
2. 结合有限雷达情报、地形、天气预报与燃油余量确认航线。
3. 任务开始后不可暂停、重置或中途退出；飞机持续沿航点飞行。
4. 玩家可以新增或调整当前目标航点之后的未来航段，已飞路径和当前目标保持锁定。
5. 飞机进入攻击区域后完成武器投放，但任务仍未结束。
6. 只有目标被摧毁且飞机进入撤离区才算成功。
7. 成功与失败都会冻结现场；失败可以返回网络重试，成功可以保存并进入复盘。

所有任务类型使用同一套飞行成功条件。情报行动、防空压制或指挥打击是它们在任务网络中的战略效果，而不是另一套飞越、侦察或摧毁雷达的独立目标模型。

具体攻击范围、速度、燃油、失败条件和航点权限见[游戏机制手册](docs/game-mechanics.md)。

## 4. 任务网络与战略收益

每个 Run 由三个顺序二选一阶段和最终打击组成。成功完成一项任务会关闭同层另一个选择并解锁下一阶段；失败不会推进网络，也不会终止整个 Run。

前置任务被刻意分配到四个正交维度：

| 任务类型 | 改变的维度 | 设计目的 |
|---|---|---|
| INTEL | 玩家可见信息 | 用更低的不确定性换取更可靠的航线判断 |
| STRIKE | 雷达扫描时间 | 减少单位时间内的扫描与探测机会 |
| SEAD | 雷达覆盖空间 | 缩小需要绕行或穿越的危险区域 |
| COMMAND STRIKE | 雷达网络协同 | 延缓指挥响应并削弱多雷达联合跟踪 |
| FINAL STRIKE | 汇总整个 Run | 用此前的选择和敌方响应组装最终防御 |

情报更准确不等于雷达变弱，覆盖缩小也不等于扫描变慢。任务收益不合并，是为了让玩家能在“看清危险”和“实际削弱危险”之间做出可感知的取舍。

每次行动还会提高跨任务敌方警戒；反复失败的代价高于成功。这使前置任务不是无成本升级，也避免通过无限试错必然抹平风险。

任务奖励倍率、警戒增长、节点状态和最终战触发条件以[机制手册的任务网络章节](docs/game-mechanics.md)为准。

## 5. 地图、地形与动态天气

### 5.1 地图是多个约束层的叠加

战术地图同时承载目标、撤离区、航点、地形、动态天气和雷达情报。Canvas 负责绘制与坐标交互，任务状态和规则计算始终由领域模型与 reducer 管理。

任务生成器会维护撤离区净空和目标区最低火控覆盖等局部约束，但当前没有对每个 Seed 做完整的数学可通关证明。生成算法保证战场结构成立，不承诺所有组合都存在显而易见的安全路径。

### 5.2 地形提供静态隐蔽

地形在单次任务中不移动，也不改变类型。它降低雷达探测概率，但不会直接改变飞机速度或燃油。静态遮蔽给路线提供可靠参照，同时也可能被敌方通过历史航迹分析识别为玩家偏好。

### 5.3 天气制造时空窗口

天气单元会移动、改变范围、强度和类型。恶劣天气能够降低探测概率，但也会减慢飞机并延长暴露时间，因此不是单纯增益。

天气状态从初始参数与任务绝对时间确定性推导，不依赖帧率。任务开始前提供固定未来时刻的带误差预报，让玩家能够规划与天气单元相遇的时机，同时保留预测不确定性。预报不是实时滚动的未来真值。

天气类型、速度损失、探测叠加与预报误差规则见[游戏机制手册](docs/game-mechanics.md)。

## 6. 雷达、防空指挥与交战

### 6.1 分层雷达网络

雷达分为远程宽波束预警、均衡目标获取和近程高质量火控三类。三类雷达分别承担早期线索、持续搜索和高质量跟踪，但任何雷达都可以凭借自身 Contact 推进交战；火控雷达只是效率最高，不是唯一能完成锁定的类型。

雷达必须同时满足真实范围和波束方向才会计算探测。距离、飞机朝向、地形、天气和雷达类型共同决定单次结果。扫描线是传感器行为的一部分，不是与模拟脱节的装饰动画。

### 6.2 敌方只能使用不完美观测

```text
Reality
  → Radar Sensor
  → Imperfect Contact
  → Belief Map
  → Air Defense Commander / Radar Operator
  → Engagement
```

只有传感器层可以读取飞机真值。探测成功后生成带位置误差、置信度和强度的 Contact；Belief Map 融合这些 Contact，并在失联后传播、扩散和衰减。Commander 与 Operator 只能消费这些不完美信息，不能为提高难度直接读取飞机坐标。

### 6.3 Operator 与 Commander 分工

每部雷达拥有独立 Operator，在广域搜索、扇区搜索和聚焦跟踪之间基于 Utility 选择动作。Commander 读取总体警戒、Belief 与雷达状态，向网络分配搜索意图和方位。

指挥链受损不会关闭雷达或取消单部雷达本地火控，而是降低决策速度、共享窗口、命令影响和联合跟踪效率。这样 COMMAND STRIKE 削弱的是“网络”，不是把每个传感器统一降级。

### 6.4 威胁反馈保持有限

正常玩家视图只通过 THREAT WARNING 告知疑似搜索、持续跟踪、锁定和导弹来袭，不指出具体威胁来源。玩家需要根据航线、雷达情报和告警变化判断如何切断连续 Contact。

雷达数值、动作阈值、Contact 生命周期、指挥链公式和导弹制导条件全部集中在[游戏机制手册](docs/game-mechanics.md)。

## 7. 情报权限与可观察性

正常任务使用带遗漏、位置误差和范围估算误差的有限雷达报告。情报权限从已完成的 INTEL 节点派生，不维护连续情报质量资源：

- 初始权限保留战前报告的不确定性。
- 第一次有效情报行动核实后续任务的全部雷达位置与型号，但不开放敌方内部状态。
- 第二次有效情报行动授权完整敌方态势，可以查看真实雷达、Contact、Belief、Commander 和 Operator。

完整态势既是正式任务奖励，也是开发环境的调试工具。两者共用显示能力，但都只能改变可见性，不能反向改变模拟结果。

锁定节点允许只读预览当前研判地图。预览和正式出击共用任务准备逻辑，因此会反映当下的任务收益、警戒和适应状态，但不会创建 Mission 或修改 Run。

## 8. 敌方跨任务响应与最终打击

### 8.1 Enemy Alert 表示战略警戒

Enemy Alert 跨任务保存，反映整个 Run 中敌方对持续入侵的响应。它会影响后续防空部署，并可能在最终任务触发额外警戒力量。它不同于单次任务内的 Awareness，也不同于针对飞机的 THREAT WARNING。

### 8.2 Enemy Adaptation 学习实际航迹

敌方适应系统只读取飞机已经飞过的轨迹，不读取计划航点。它分析地形利用、南北航路和直达倾向，用空间关系选择需要调整的雷达。成功航迹比失败航迹权重更高，但失败重试仍会留下有限情报价值。

这种设计让敌方形成可解释但可能被误导的画像。玩家可以改变习惯规避反制，也可以主动制造错误历史偏好。

### 8.3 Final Strike 汇总整个 Run

最终打击在基础任务上组装目标区火控、警戒增援和适应性拦截力量，再应用前置任务形成的扫描、覆盖、指挥链和情报结果。它不是普通任务换名，而是对整条战略路线的结算。

精确警戒阈值、画像特征、移位强度和增援规则见[游戏机制手册](docs/game-mechanics.md)。

## 9. 行动代码与确定性生成

`OPERATION CODE` 是整个 Run 的根 Seed，作用类似 Minecraft 世界种子。字符串先映射为确定性整数状态，再驱动伪随机序列。任务网络、节点内容、雷达情报、天气预报、最终战增援和逐次雷达探测使用彼此隔离的命名子随机流。

隔离随机流是重要扩展原则：新增天气参数不应改变雷达遗漏结果，增加一次 UI 预览也不应消耗正式任务的探测随机数。

基础任务生成后，系统再按固定顺序应用任务收益、Enemy Alert、Enemy Adaptation、Final Strike 增援和安全约束，最后生成玩家情报。这样情报永远引用最终部署，而不是已经被后续规则移动或替换的雷达。

具体哈希算法、子 Seed 命名和任务准备顺序见[游戏机制手册](docs/game-mechanics.md)。

## 10. 复盘、持久化、事件与音效

成功撤离时保存冻结快照，而不是保存一场继续运行的 Mission。任务视角复盘还原当时玩家拥有的信息，全景复盘则展示成功瞬间的完整敌方内部状态。两种视角都只读取历史，不重新推进天气、雷达或 Commander。

Run、任务网络、当前 Mission 和成功复盘保存在浏览器本地。运行中刷新会继续执行，不会利用刷新制造暂停。界面语言使用独立偏好，不污染游戏存档。

音效由领域事件驱动。短事件产生一次性音效，锁定和导弹告警使用可清理循环音；任务结束、脱锁或组件卸载必须停止循环。事件历史设置上限，音频按事件唯一 ID 消费，避免重渲染重复播放。

## 11. 代码架构

```text
src/core        确定性随机数等基础设施
src/config      地图、飞机、雷达和交战参数
src/domain      航线、雷达、Contact、Belief、Commander、天气与任务网络纯逻辑
src/procedural  Seed 驱动的任务与任务网络生成
src/game        RunState、reducer、帧循环、任务准备与持久化
src/i18n        语言目录、语言上下文与旧简报兼容翻译
src/ui          React 战术终端、Workspace 与 Canvas 地图
src/audio       领域事件驱动的 Web Audio 音效
```

### 11.1 核心状态边界

- `RunState` 保存整个任务网络、持久敌情、当前 Mission 和成功复盘。
- `MissionSession` 保存一场可运行任务的实时状态。
- `MissionDebrief` 是冻结快照，不能重新作为可运行 Mission 使用。
- reducer 是任务状态变化的唯一事实来源。
- Canvas 只负责绘制和坐标交互，不持有第二套游戏状态。
- 共享 UI 组件只接收只读数据和回调，不直接修改 `RunState`。
- 本地化只发生在渲染边界；领域枚举、Seed 和持久状态不保存展示语言。

### 11.2 必须保持的不变量

- 只有 Radar Sensor 可以读取飞机真值；后续敌方 AI 只能消费 Contact。
- 普通视图不能通过图例、列表或高亮泄露真实雷达位置。
- 完整敌方态势与开发调试只改变显示，不能改变任务计算。
- 正式出击与锁定节点预览共用任务准备规则。
- Seed 驱动结果不得依赖帧率。
- 航点权限同时由 UI 和 reducer 保护，不能只依赖按钮置灰。
- 所有任务只有“摧毁目标并撤离”一种成功口径。
- 语言选择只能改变表达层，不能派发任务动作或改变模拟时序。

新增机制时应优先把纯计算放入 `domain`，由 reducer 编排状态演进，再由 React 与 Canvas 消费结果。不要在 UI 中实现第二套雷达、任务或权限规则。

## 12. 开发与发布

安装与本地运行：

```bash
npm install
npm run dev
```

提交前验证：

```bash
npm run typecheck
npm run test
npm run build
```

`main` 分支通过 GitHub Actions 构建并发布到 GitHub Pages。Vite 使用相对资源基址，使同一构建兼容本地预览与仓库子路径。
